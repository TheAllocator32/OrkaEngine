# OrkaShaderC

(Not so) tiny CMake helper for turning BGFX shader sources into something Orka can actually eat.

It supports two workflows:

* compile shaders into runtime binaries
* bake shaders directly into C++ headers

No big ceremony. No shader-pipeline religion. Just builds the damn shaders.

## Functions

### `shader2shader(...)`

Compiles `.sc` / `.shader` files into backend-specific runtime shader binaries:

```txt
.gln.shader
.vk.shader
.dx11.shader
...
```

Use this when shaders should live as external runtime assets.

Notes:

* creates a normal custom target, not `ALL`
* you decide which targets depend on it
* automatically registers its install hook
* output format matches `primitives/Shader.hpp`

### `shader2code(...)`

Converts shader stages into a generated C++ header.

Expected naming:

```txt
name.vert.shader
name.frag.shader
```

Also supported:

```txt
name.vs.*
name.fs.*
```

Matching vertex and fragment stages are merged into:

```txt
name.autogenerated.shader.hpp
```

Generated symbols look like:

```cpp
name_vert_GL
name_frag_vulkan
```

Unsupported host platforms still get stub symbols, so the compiler doesn't rage just because Metal is not available on Linux.

Notes:

* creates an `ALL` target by default
* overwrites old autogenerated headers
* removes obsolete per-stage generated headers after merging
* best choice when shaders should be embedded into the binary

## Minimal example

```cmake
include("OrkaShaderC.cmake")

shader2shader(
    ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}/src"
    TARGET shader_binaries
)

shader2code(
    ROOT_DIR "${CMAKE_CURRENT_SOURCE_DIR}/src"
    TARGET shader_headers
)

add_dependencies(YourMainTarget shader_headers)
```

Runtime shader binaries are install-aware automatically:

```cmake
shader2shader(...)
```

That’s it. Shaders go in, engine food comes out. Unless you mess it up yourself...
